# ตัดสินวิธีนับครั้งแรกตอนรับเข้า — Design Spec

วันที่: 2026-10-12
สถานะ: รอ user รีวิวสเปคก่อนเขียนแผน

## 1. ความเข้าใจร่วม (Intent)

- ผลลัพธ์: สร้างสินค้าไม่ต้องเลือกวิธีนับ (default รายชิ้น) วิธีนับจริงตัดสินตอนรับเข้าครั้งแรก
- ผู้ใช้: พนักงานรับของที่บางทีไม่รู้ว่าแบบไหนจนของมาถึง
- ความสำเร็จ: เลือกผิดสลับได้อิสระจนกว่าจะบันทึกสำเร็จครั้งแรก, ครั้งต่อไปล็อกตามเดิม, serial ซ้ำไม่เข้า DB (ของเดิม: คิว pending + confirm)
- สมมติฐาน: ไม่แตะ schema, ของมีประวัติแล้วกฏล็อกเดิมทุกอย่าง

## 2. ขอบเขต

แตะ:
- `ProductsClient` ฟอร์มเพิ่ม: ตัด dropdown วิธีนับ/หน่วยนับออก (default SERIAL/ชิ้น)
- `ProductsClient` ฟอร์มแก้ไข: วิธีนับโชว์อ่านอย่างเดียว
- `scan-in/page.tsx` preload: เพิ่ม flag `hasHistory` (มี unit/stockQty/scanLog ไหม)
- `ScanInClient`: ถ้าสินค้าไม่มีประวัติ โชว์ tabs ยิง serial/กรอกจำนวน (+เลือกหน่วยนับ), PATCH วิธีก่อนบันทึกครั้งแรกที่สำเร็จ

ไม่แตะ:
- schema.prisma, API กฏล็อก (`409` เดิม), scan-out/audit/reports, ScanConsole

## 3. Section 1 — กฏข้อมูล (อนุมัติแล้ว)

- สร้างใหม่ = SERIAL + เปลี่ยนได้อิสระจนกว่าจะมีของ/ประวัติ (API เดิมรองรับอยู่แล้ว)
- มีของ/ประวัติแล้ว = ล็อก เปลี่ยนไม่ได้ (`409` เหมือนเดิม)

## 4. Section 2 — หน้ารับเข้า (อนุมัติแล้ว)

- สินค้าไม่มีประวัติ: tabs ยิง serial / กรอกจำนวน (+ dropdown หน่วยนับมาตรฐาน/พิมพ์เอง)
- สลับ tabs ได้อิสระจนกว่าจะบันทึกสำเร็จครั้งแรก (ของค้างในคิว + สลับข้ามวิธี = บล็อกให้เคลียร์คิวก่อน)
- กดยืนยัน/บันทึกครั้งแรก: PATCH วิธีนับ (+หน่วยนับ) ก่อน แล้วรับของ — ล้มเหลว = ไม่ล็อก เปลี่ยนได้ต่อ
- สินค้ามีประวัติ: ใช้วิธีเดิม ไม่มี tabs

## 5. Section 3 — ฟอร์มสินค้า + Testing (อนุมัติแล้ว)

- ฟอร์มเพิ่ม: เหลือ SKU/ชื่อ/แบรนด์/ประเภท
- ฟอร์มแก้ไข: วิธีนับอ่านอย่างเดียว
- unit: กฏล็อกเดิม, integration: รับครั้งแรกสลับวิธีได้ + ครั้งที่สองล็อก (`409`), e2e: สร้าง → รับแบบจำนวน → เปิดใหม่ไม่มี tabs
